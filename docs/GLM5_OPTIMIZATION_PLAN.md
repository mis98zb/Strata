# GLM 优化思路与测量依据

测量日期：2026-11-05 至 2026-11-06。

本文件记录 GLM 实验分支的瓶颈、优化方向和验证要求，不代表所有方案已经实现。
实现与历史性能记录见 [GLM5_NEXT.md](GLM5_NEXT.md)。
探针口径见[阶段探针说明](GLM5_NEXT.md#phase-probes-transfer-and-cpu-checks)。

## 一、测量结果

本节保留 CPU 工作池优化前的瓶颈基线。最新进展见[第一批优化结果](#六第一批优化结果cpu-专家工作池与行分片)。

### 1. 测试条件

- 硬件：RTX 3080，报告显存 20 GiB；Xeon W-2133，6 核 12 线程；247 GiB RAM。
- 当前 PCIe 链路：3.0 x16。
- 模型：六分片 Huihui GLM-5.3-Flash UD-Q4_K_XL。
- 输入：保存的重复文本 token，短输入取同一份 200000-token 输入的前缀。
- 执行方式：整层 prefill、DSA、Flash Attention、tail 0、MTP 关闭。
- 预算：prefill GPU 14336 MiB、host 32768 MiB、GPU reserve 1024 MiB。
- 除缓存扫描外，decode 专家缓存上限为 4096 MiB，并根据 prompt 热度预热。
- 环境：`STRATA_MMQ_KQ=1 CUDA_MODULE_LOADING=LAZY NVIDIA_TF32_OVERRIDE=0 OMP_WAIT_POLICY=PASSIVE`。
- 环境共享，未锁定 CPU/GPU 时钟；以下不是通用速度保证，也不是质量测试。

### 2. 阶段探针结果

| 场景 | 总墙钟时间 | 关键阶段 | 测量结果 |
|---|---:|---|---:|
| 8192 输入，prefill | 40.064 s | 暴露的权重加载等待 | 19.553 s，接近一半 |
| 8192 输入，64 输出 | decode 17.248 s | CPU 专家阶段 | 13.504 s，约 78% |
| 200000 输入，prefill | 483.322 s | 暴露的权重加载等待 | 1.751 s |
| 同上 | 同上 | MLA mixer | 156.778 stream seconds |
| 同上 | 同上 | KDA mixer | 70.610 stream seconds |
| 同上 | 同上 | 路由 GPU 专家 | 133.164 stream seconds |
| 200000 输入，32 输出 | decode 8.508 s | CPU 专家阶段 | 6.536 s，约 77% |

长输入 prefill 的主要传输：

- 权重上传：181.09 GiB。
- 激活边界 H2D：500.49 GiB，74.329 stream seconds。
- 激活边界 D2H：488.28 GiB，64.566 stream seconds。
- 权重加载基本被计算遮住，但激活往返仍然很大。

长输入 decode 的两个对照：

- 缓存晋升上传：0.7615 GiB，host 0.140 s、stream 0.133 s，不是主要耗时。
- 路由回读：仅 0.0205 GiB，但 host 0.919 s、stream 0.035 s。
  host 调用还在等前面的 GPU 工作，不能把它解释为 PCIe 搬运本身很慢。

**读取规则：**

- `host_ms` 是主机操作的墙钟耗时，不等于纯 CPU 算术时间。
- CPU 专家阶段包括量化、解包、dot、分配及 OpenMP 调度。
- `stream_ms` 是 CUDA event 区间，可能包含主机提交空档，不是纯 kernel-busy 时间。
- MLA/KDA/FFN/router 是 `layer_pre` 的子区间；不同流也会重叠，不能直接相加。
- CPU 专家 `bytes` 是逻辑权重读取量，不是 PMU 测得的 DRAM 流量。
- 已计数的传输 payload 不是全部 PCIe 总线事务；不能直接用“总字节数 ÷ 带宽”当墙钟耗时。

### 3. CPU 线程与缓存扫描

以下是同一轮 8192 输入、64 输出的扫描，与上面的最终阶段细分不是同一轮。
不要混用不同轮次的数据计算细微速度变化。

| CPU 线程 | 缓存选择 | 实际缓存 | Decode |
|---|---|---:|---:|
| 1 | 4096 MiB 上限 | 3685.1 MiB，252 槽 | 2.216 tok/s |
| 3 | 同上 | 同上 | 3.529 tok/s |
| 6 | 同上 | 同上 | 3.840 tok/s |
| 6 | 自动预算，reserve 不变 | 7984.4 MiB，546 槽 | 4.332 tok/s |

- 缓存命中率：32.55% → 50.03%。
- 64 个输出的 CPU 逻辑权重读取量：207.43 GiB → 153.81 GiB。
- 3 → 6 线程的收益较小，不能假设增加线程就能线性提速。
- 自动缓存的结果只在这个 8k 样本上测过，不能直接外推到 200k。
- 该轮不同配置的完整 prefill logits 和输出 ID 均相同；这不证明所有缓存配置普遍数值等价。

### 4. 带宽与 AVX-512

独立校准使用 1 GiB 数组做四轮校验和读取，以及每方向五次 256 MiB pinned CUDA 拷贝。
校验和、PCIe 往返 payload 均一致。下面使用十进制 GB/s。

| 项目 | 实测 |
|---|---:|
| 内存连续读取，1 线程 | 12.711 GB/s |
| 内存连续读取，3 线程 | 35.245 GB/s |
| 内存连续读取，6 线程 | 38.678 GB/s |
| Pinned H2D | 7.907 GB/s |
| Pinned D2H | 8.395 GB/s |

- CPU 支持 AVX-512F/BW，不支持 AVX-512 VNNI/BF16。
- ggml CPU 代码已经使用 `-march=native`，不能根据缓存中的 `GGML_AVX*=OFF` 判断没有 SIMD。
- 实际 Q4_K/Q5_K/Q6_K dot 反汇编使用 YMM，没有 ZMM 或 VNNI 指令。
- 当前热点主要仍是显式 256 位实现，不会因为打开一个 AVX-512 选项就自动变成 512 位。
- CPU 专家阶段是瓶颈，但尚无 PMU 数据区分 DRAM 等待、解包、算术和调度各自的比例。

## 二、优化思路

下面都是候选方向，除注明的现状外，收益均待实测。
优先级按目标场景划分，不能把短 prefill、长 prefill 和 decode 混为一谈。

状态标记：

- `[ ]` 未做：尚未实现或尚未完成所述验证。
- `[x]` 已做：已实现或已完成所述测量，不代表所有硬件都验证过，也不代表一定有速度收益。
- ❌ **已拒绝**：当前不采用的具体方案，附上原因；不表示拒绝整个优化方向。

`[ ]` 和 `[x]` 使用 Markdown 原生复选框；已拒绝的事项使用 ❌ 图标。
分类标题和约束说明不标状态，只给具体工作项标状态。

- **GPU 计算优化**
  - **算子优化**
    - MLA：长 prefill 优先。
      - [x] 批量准备兼容的各头输入量化；矩阵乘法仍逐头独立执行。
      - [x] 分别测 query、absorb、KV、indexer 投影/池化/打分/选择、attention、deabsorb、output 和布局转换。
      - [ ] 进一步拆解 attention 内核中的 QK、softmax、PV 和补偿计算。
      - [x] 同一 BatchGemm stream 上复用未改变的整数 bounds，避免各头和专家产品重复初始化元数据。
      - [x] Flash 直接读取、写入 head-major 图像，移除 attention 两侧的转置和两个临时图像；见[本轮结果](#十二mla-直接使用-head-major-布局)。
      - [x] Flash 用三个半块轮转和 `cp.async` 预取 KV，保持原 32-cell 分块和累加顺序；见[流水化结果](#十三mla-kv-加载流水化)。
      - [x] F32 indexer 四查询 tile 提前准备下一段 query/key，保留原 FMA 和 head 求和顺序；见[本轮结果](#十七indexer-寄存器预取流水化)。
      - ❌ **已拒绝**：用额外 shared-memory 暂存和 `cp.async` 流水化 indexer；增加中转和资源占用，微基准变慢。
      - [ ] 继续减少逐头提交、重复准备和中间缓冲读写。
      - [ ] 研究批量矩阵接口，但保持单头的维度、精度和累加语义。
      - ❌ **已拒绝**：以全局查询预分解替换块内查询准备，虽降低 shared memory，但微基准没有稳定收益。
      - ❌ **已拒绝**：把 F32 indexer query tile 从 4 改成 2，虽然资源占用变小，打分反而更慢。
    - 路由专家：长 prefill 优先。
      - [x] 批量专家行 gather/scatter、稳定计数分组和路由缓冲复用。
      - [x] 在明确的输入生命周期内，复用兼容 gate/up 的量化准备。
      - [ ] 减少逐专家、逐投影的小提交，检查主机供给空档。
      - [ ] 研究“大外层 batch + 小 mixer 子批”，增加每个专家拿到的有效行数。
      - [ ] 统计实际专家行数分布；2048 tokens、top-8、288 专家时，均匀估算只有约 57 行/专家。
      - ❌ **已拒绝**：将此前未通过数值一致性检查的多专家 MMQ 实现设为默认路径。
        - 原试验改变了累加行为并影响输出，已撤掉；新的集合执行方案仍可独立研究。
    - Decode 小算子。
      - [x] 单 token 的 GPU 专家直接使用当前输入，量化一次供该次派发的专家复用，并直接写入输出槽。
        - 保持原来逐专家、逐投影的单列矩阵乘法；不改变 gate/up/down 的维度和累加。
        - 多 token 或重复路由仍走原路径；没有缓存跨派发的输入量化结果。
      - [ ] 继续检查多 token、投影间准备及其他中间缓冲的重复工作。
      - [ ] 研究路由集合级执行和安全融合，避免逐专家重复准备同一输入。
      - 这是 decode 调度问题，不等于直接恢复此前撤掉的 prefill 多专家 MMQ。
    - Scratch 与布局。
      - [x] 清理未使用的单 token workspace 和旧 Q8_K/Q8_0 图像分配。
      - [x] 直接布局的 Flash 路径不再分配 token-major `qabs/kqv`；batch 2048 时实测少用 512 MiB。
      - [ ] 继续按阶段生命周期复用临时空间，减少不必要的 D2D 和转置。
      - 保持 sizing/init 一致，不能覆盖持久 KDA、MLA、NextN 状态。
  - **Tensor Core 利用**
    - [x] 确认当前 Flash 编译结果包含 `HMMA.16816.F32`，不是标量实现冒充 Tensor Core 路径。
    - [ ] 按权重格式、矩阵形状确认实际指令路径，不把“调用 MMQ”当成利用率证明。
    - [ ] 用硬件 profiler 检查 Tensor Core 活跃度、occupancy、访存和小矩阵效率。
      - 已尝试 Nsight Compute，但设备性能计数器权限被拒绝，实际利用率尚未测得。
    - [ ] 改善有效 batch、布局和提交粒度，再判断是否需要替换矩阵路径。
    - 单 token decode 的小 GEMV 不一定适合靠 Tensor Core 解决。
    - FP16/BF16/TF32 替换属于算术策略变化，不能当作无损优化直接启用。
  - **启动与控制开销**
    - [ ] 找到大量小 kernel 和 CPU 提交间隙后，再评估融合或有限 CUDA Graph。
    - Graph 需要稳定地址、明确状态和缓存失效规则，不是当前第一优先级。

  - **缩短无法隐藏的加载与传输**

  - **减少不必要的传输**
    - [ ] 优先检查长 prefill 约 989 GiB 的激活边界往返。

      - [ ] 继续研究能否在预算和原规划优先级允许时增加驻留/分组，减少往返。

## 三、建议推进顺序

| 目标 | 第一优先级 | 后续方向 |
|---|---|---|
| Decode | CPU 基础优化和当前长短上下文缓存基线已做；下一步研究缓存策略和 CPU/PCIe 分工 | 逐专家 GPU 派发、AVX-512 专用内核 |
| 长 prefill | 已分测 MLA；继续研究 attention、indexer 打分及专家有效 batch | 激活边界往返、剩余 overlap 和 scratch 复用 |
| 短 prefill | 暴露的权重加载链路 | 减少打包/转换/提交与必要传输成本 |

先做有阶段证据的改动，再考虑大规模重构或精度路径变化。
不因为 CPU 专家耗时高，就认定 GPU 算子、传输和缓存已经没有优化空间。

## 五、每项优化的验收要求

- **性能**
  - 同输入 ID、输出长度、量化、预算、上下文、线程数和缓存策略做 A/B。
  - 改缓存或线程数时，其余条件不变，分别报告命中率和 CPU 读取量。
  - 尽量正反顺序复测；记录环境波动、初始化、prefill、decode setup 和 decode。
  - 不把 stream 时间、调用数减少、微基准加速当成端到端收益。
- **正确性**
  - 现有保序路径比较完整 logits、输出 ID、KDA/MLA/NextN 状态。
  - 覆盖尾批、不同格式、append/reset、MTP 接受/拒绝和 prefill/decode 交接。
  - 改变精度或累加语义的方案必须单独说明，不降低原路径阈值来迁就新实现。
- **资源与边界**
  - 维持“整层必须放下 → 尽量大 batch → prefetch → 多层分组”的规划优先级。
  - 计入显存、普通内存、pinned 内存和新增 scratch，不能用未计数分配绕过预算。
  - 优先局限在 GLM 私有代码；默认路径和其他模型不随实验变化。
  - 运行相关回归测试和必要的 sanitizer；未测硬件、未测路径明确列出。

## 六、第一批优化结果：CPU 专家工作池与行分片

### 1. 本批做了什么

- [x] 常驻工作池，线程数包含主线程，`cpu_threads=6` 时创建 5 个辅助线程。
- [x] gate/up 和 down 的输出行按 64 行分块，避免只按整个专家分配任务。
- [x] 两阶段之间等待所有行完成，再用原量化器准备完整 hidden，保持原 block scale 语义。
- [x] 复用 hidden、量化 scratch 和输入激活缓冲；gate/up 的激活格式相同时只准备一次。
- [x] 缓存层内的只读权重布局与 CPU trait，减少重复查询。

没有修改 ggml dot、SwiGLU/clamp 或每行内部的累加顺序，也没有新增 AVX-512 kernel。

## 七、第二批优化结果：单 token GPU 专家直接执行

### 1. 本批做了什么

### 2. 现有热度配额是否有用

本批没有改热度算法，也没有改默认值。测试的是已经存在的可选参数：

```text
--glm-gpu-warm --glm-gpu-heat-quotas
```

硬件、六分片 Q4_K_XL、环境变量、6 线程 CPU 工作池和 GPU 单 token 直接路径沿用前两批。
Prefill GPU/host/reserve 仍是 14336/32768/1024 MiB，decode reserve 1024 MiB，MTP off。
每种输入只执行一次 prefill，再从同一个 host checkpoint 重建 decoder，
按 equal/heat/heat/equal 运行；每次 decode 都重新建立并预热独立缓存。
这样不把不同 prefill 的热度差异混入对照。

即使都指定 4096 MiB 上限，实际分配也不同：
等额配额必须给每层相同槽数，留下约 411 MiB 未使用；热度配额能使用更多剩余预算。
所以“同一上限”不等于“同一实际显存”。
为此又在等额实际占用向上取整到 MiB 的预算下运行两次热度配额，
其实际占用略低于等额基线。

200000 输入、128 输出的结果：

| 项目 | 等额配额 | 热度配额，同 4096 MiB 上限 | 热度配额，近似同实际显存 |
|---|---:|---:|---:|
| 实际缓存 | 3685.13 MiB，252 槽 | 4089.94 MiB，281 槽 | 3682.88 MiB，253 槽 |
| 命中率 | 37.46% | 44.24% | 41.39% |
| CPU 逻辑读取量 | 384.90 GiB | 344.03 GiB | 361.42 GiB |
| Decode，tok/s | 6.253 / 5.974 | 6.636 / 6.659 | 6.255 / 6.311 |
| 合并样本吞吐 | 6.111 tok/s | 6.647 tok/s | 6.283 tok/s |
| 相对等额吞吐 | 基线 | +8.78% | +2.82% |

8k 输入、128 输出的同类对照：
等额合并 5.956 tok/s，热度同上限 6.096 tok/s，
近似同实占 6.012 tok/s，分别约 +2.34% / +0.94%。
这组热度配额的实际占用为 4090.19/3683.13 MiB。

这些样本说明现有热度配额可以减少 miss；同上限下的收益还包含使用原本未分配预算的效果。
近似同显存的收益更小，且不是交错的 ABBA，环境时钟和其他用户未隔离。
不能承诺普遍提升 8.78%，也不能把已有选项的效果算成新算法的收益。
更大的实际缓存还会增加预热成本；用户的显式上限始终保留。

本轮各个 200k 配置的完整 prefill logits 和全部 128 输出 ID 都与原保存结果逐字节相同；
8k 配额变体的完整 logits 和 128 输出 ID 也相同。
改变缓存配额会改变 CPU/GPU 放置，本样本一致不代表任意输入都逐字节一致，
所以热度配额仍需显式选择，没有自动替用户开启。

## 九、CPU 调度实验：两项不保留

这轮先尝试减少工作池调度竞争，没有因为代码看起来更简单就修改默认策略。
以下两版均未修改 dot、量化、SwiGLU/clamp 或每行累加顺序。

### 1. 静态连续行块分配

每个 worker 一次取得自己负责的连续行块范围，不再逐块抢原子任务。
测试保持 64 行块，主线程也参与，并保留原来的两阶段同步。

| 8192 输入 / 128 输出 | 动态 64 行块，tok/s | 静态连续块，tok/s | 合并样本变化 |
|---|---:|---:|---:|
| 6 线程 | 6.317 / 6.284 | 4.996 / 5.033 | -20.41% |
| 3 线程 | 4.912 / 4.944 | 4.824 / 4.834 | -2.00% |

六线程 CPU 专家阶段约从 13.85/13.94 s 增加到 19.10/18.89 s。
静态分配省去了逐块原子领取，但没有缩短关键路径，不能认为原子操作就是主要瓶颈。
工作线程调度、负载尾部或访存行为可能影响结果，尚未用 PMU/亲和性实验拆开归因。

### 2. 保留动态领取，扩大到 128 行块

继续使用原子抢任务，但每个任务处理 128 行，减少任务数；不采用上面的静态分配。

| 8192 输入 / 128 输出 | 动态 64 行，tok/s | 动态 128 行，tok/s | 合并样本变化 |
|---|---:|---:|---:|
| 6 线程 | 6.265 / 6.273 | 6.203 / 6.195 | -1.12% |
| 3 线程 | 4.945 / 4.921 | 4.908 / 4.897 | -0.61% |

这里差异较小且共享环境未隔离，但没有证据支持把 128 行设为默认值。

### 3. 测量条件与决定

- 沿用同一 RTX 3080/W-2133、Q4_K_XL、DSA/Flash/tail 0、MTP off、
  CPU 工作池和 GPU 单 token 直接路径。
- 专家缓存仍为 4096 MiB 上限，实际 3685.13 MiB/252 槽，不启用热度配额。
- 预算和环境变量沿用前面的对照，context 为 8320。
- 每个线程数和实验各用同一个 prefill checkpoint，
  按动态基线/候选/候选/动态基线运行，均生成 128 个 token。
- 两项实验共 16 次 decode 的完整输入 logits、全部输出 ID、
  cache hits/misses、CPU 逻辑读取量和上传量都一致。
- 静态分配的混合格式、尾部任务和 MTP 测试通过，
  CPU 工作池翻译单元的 TSAN、ASAN/UBSAN 检查也通过；拒绝原因是性能，不是数值错误。
- **两项实验代码和专用执行选项均已撤掉。保留动态 64 行工作池，没有新增用户开关。**

本结论只拒绝这两种具体实现，不表示今后不再研究负载均衡、任务粒度或 CPU 亲和性。

## 十、CPU 结果合并上传：调用少了，但没有稳定提速

在上面两项 CPU 调度实验失败后，又尝试了不改变计算的传输优化：
只将相邻 CPU miss 输出槽合并为一次 H2D，不跨过 GPU 已写好的输出槽，
不增加打包缓冲，不改变传输总字节数、缓存放置和算术。

- ❌ **已拒绝**：当前相邻输出合并实现。没有稳定端到端收益，代码、辅助分段函数和执行选项已移除。

### 2. 两个算子实验没有保留

- **全局查询预分解。**
  - 将原 Flash 的高/低半精度查询分解提前到调用者 scratch。
  - 保留原 MMA、online softmax、补偿累加及其顺序；没有改用更低精度。
  - 按结构体和 launch 参数，块内动态 shared memory 从 71120 B 降到 37824 B；
    编译资源报告中的寄存器却从 211 增加到 250，无 stack/local spill。
  - 64 查询、64 heads、50000 cached cells、2048 selected cells 的微基准，

  - Dense/sparse、因果与无效索引、零输入和大动态范围的输出字节、输入不变性及保护区检查通过。
    没有接入模型执行器，也没有宣称实模型加速。
  - 实验实现、API 和专用测试入口已移除，保留原 Flash。
- **F32 indexer 的两查询 tile。**
  - 保留 128 维 FMA 顺序和 32 heads 求和顺序，只改变独立输出的分块。
  - 编译资源由 93 registers / 32768 B shared 变为 53 registers / 17408 B shared。
  - 64 查询、50000 pools 下，原四查询 tile 约 1.91–1.95 ms，

  - 两查询 tile 使逻辑块数和池化键 tile 的重复加载次数加倍，

  - 完整 score 字节、保护区、pruning、MTP 接受/拒绝、append 和状态检查通过。
    实验实现和控制字段已移除，保留四查询 tile。

这两项都说明：更少的寄存器/shared memory 或更高的理论 occupancy，
不能直接当成性能收益。

Flash 的 SASS 中可以确认 `HMMA.16816.F32`，确实在使用 Tensor Core。
已尝试 Nsight Compute 的 LaunchStats/Occupancy/SpeedOfLight，
但收到 `ERR_NVGPUCTRPERM`，没有获得实际 Tensor Core 利用率和 achieved occupancy；
没有修改系统权限或以资源上限推算冒充硬件采样。

### 3. 保留一个不改变计算的简化

`BatchGemm::native` 原来为每个 MMQ 产品启动一次 kernel，写入同一组整数 `{0, columns}`。
现在在原 SM86 modern compute 路径中，只有列数改变才重写：

- 这两个整数只由该 backend 在自己的唯一 compute stream 上写入。
- 连续同列数的各头、gate/up/down 和其他产品复用它，不缓存浮点输入。
- 列数改变立刻重新写入；FP16/F32 回退不修改这份数组。
- backend 销毁时缓存结束；现有执行器不使用 CUDA Graph，不能未经验证推广到图回放。
- 无新增 GPU/host tensor 分配、传输或 CLI 开关；reference 和未验证设备保留原初始化方式。

## 十二、MLA 直接使用 head-major 布局

### 1. 改了什么

原路径把 absorb 的 head-major 输出转成 token-major，运行 Flash，
再把 attention 输出转回 head-major 供 deabsorb 使用。
现在 Flash 直接读写已有的 head-major 图像：

- 删除这两次转置，不再分配中间的 `qabs/kqv`。
- 保持原 MMA、online softmax、补偿累加及顺序，只改变地址计算。
- 保留前面的 query 拆头和最后的输出合头；不是删除全部 MLA 转置。
- 按完整 batch 的跨度定位 head，支持稀疏窗口偏移和尾部；空选择窗口按 head 清零。
- 单 token 时两种布局相同，直接复用原 kernel。这个特化晚于下面的性能测量，
  不据此宣称 decode 提速。

自动选择只覆盖已验证的 CUDA SM86、显式启用 Flash、
KV rank 512、head width 256 的配置。`--reference` 和未验证设备保留 token-major；
关闭 Flash 时仍分配原路径需要的 scratch。没有增加普通 CLI 速度开关。

其他已保留优化均开启。

## 十三、MLA KV 加载流水化

### 1. 不改变算术，只重排 KV 加载

原 Flash 每次处理 32 个 cached cells：加载 KV，完成 QK、softmax 和 PV，再加载下一块。
新路径保持上述计算、分块和补偿累加顺序，使用 CUDA `cp.async` 将下一块的一半
加载到第三个半块缓冲，与当前块的 softmax/PV 重叠。
PV 完成后再复用已释放的半块，加载下一块的另一半。

- 三个半块按环轮转，块边界等待异步复制完成，再由线程块同步确认所有线程可读。
- 无效、未来及越界 cell 使用异步零填充，不读取非法地址。
- KV 数据仍是 F16，Q、概率分解和 F32 MMA/补偿求和均未变。
- 自动选择限 CUDA SM86、显式 Flash、KV rank 512、head width 256。
  Reference 和未验证设备保留原直接加载。私有 `FlashKvLoad` 可隔离 A/B，没有普通 CLI 开关。
- `kv_load=prefetch|direct` 显示实际选择；关闭 Flash 不会因该选项开启 Flash。

这里的 shared memory 是线程块使用的片上内存，**不是 20 GiB 显存**。
原 kernel 需要 71120 B，完整双缓冲需要 104400 B，超过 SM86 每线程块 99 KiB 的上限。
三个半块需要 87760 B，可以放下。增加全局显存预算不能扩大这个片上上限。
Head-major 编译资源由 211 增至 234 registers，singleton 使用的 token-major
由 215 增至 248 registers；均没有 stack/local spill。这不是实际 occupancy 测量。
没有增加全局 GPU tensor 或 host/pinned 缓冲，上一轮节省的 512 MiB prefill scratch 保留。

这里保留旧 prefill 预算是为了隔离内核收益，不是给 decode 预留显存。
独立 prefill 完成后才建立 decode 专家缓存；扩大 prefill 预算是另一项对照。
需要留出驱动和未计入分配的安全余量，不能把所有空闲显存都算成可用 tensor 预算。

## 十四、CPU Q4_K 多行与 AVX-512 原型

### 1. 范围和实现

先检查实际模型的 routed expert 矩阵格式：Q4_K 82 个、Q5_K 41 个、Q6_K 3 个。
这轮先针对 Q4_K；没有把 Q4_K 原型的结果外推到其他格式。
当前 x86 ggml 的相应 dot 只支持 `nrc == 1`，不能直接把参数改成多行。
仓库已有的 K-quant 批量接口主要复用同一权重行供多个 token 使用，
也不是普通单 token decode 所需的“一个激活、多个输出行”。

隔离原型使用原模型第一层 MoE gate 的真实 Q4_K 权重，比较四种方案：

- 两行 AVX2：复用 Q8_K 激活加载和 block sums，每行独立累加。
- 四行 AVX2：同样的方式扩大行数。
- 双行 AVX-512：用 ZMM 的两个半部处理独立输出行，分别按原顺序归约。
- 单行 AVX-512 整数宽化：只合并整数部分，回到原八路 F32 FMA 和原浮点归约。

以上均保留原激活量化、Q4_K scales/mins 计算和每行浮点累加顺序。
不同输出行的权重不同，不能因为激活相同就省掉各行自己的权重读取和解包。
另外尝试展开固定行数/子块循环，避免把第一版的数组和循环开销误认为 SIMD 的必然代价。
原型遵循 ggml 的 MIT 许可，只保存在会话实验目录，没有修改公共 ggml 或其他模型路径。

### 2. 测量

硬件仍为 Xeon W-2133，`OMP_WAIT_POLICY=PASSIVE`，动态 64 行分块，
1/3/6 线程。每个专家为 2048 行、4096 列；扫描 1/16/64 个专家，
分别对应 4.5/72/288 MiB 权重工作集。
每种方案先预热，再运行十次取单次平均；各线程配置按原路径、各候选、各候选反序、
原路径的次序测量。共享环境未锁定频率。

下面是最后一轮 288 MiB 工作集的数据；每格是前后各一个样本，单位 ms，越小越好：

| 线程 | 原 ggml 单行 | 两行 AVX2 | 四行 AVX2 | 双行 AVX-512 | 单行整数宽化 |
|---|---:|---:|---:|---:|---:|
| 1 | 33.897 / 34.269 | 43.306 / 44.103 | 41.147 / 41.803 | 36.856 / 36.666 | 34.636 / 34.690 |
| 3 | 11.865 / 11.681 | 16.549 / 16.722 | 16.114 / 15.641 | 14.841 / 15.145 | 11.777 / 13.093 |
| 6 | 7.091 / 7.437 | 9.940 / 9.765 | 9.783 / 9.506 | 9.352 / 8.976 | 7.366 / 7.390 |

六线程合并样本中，两行/四行 AVX2 耗时分别约增加 35.6%/32.8%，
双行 AVX-512 约增加 26.2%；单行整数宽化约增加 1.6%，接近持平。
72 MiB 的前几轮同样没有稳定改善；小工作集个别组合更快，但原路径本身也有明显波动，
不能据此启用默认优化或宣称真实 decode 提速。

反汇编确认了多行原型的数组/寄存器中转，因此补做循环展开再复测。
展开没有扭转较大工作集的结论。AVX-512 版本确实生成 ZMM 指令，
但没有 PMU/频率采样，不能把变慢直接归因于 AVX-512 降频、内存带宽或某一类 stall。
逻辑权重 payload 也不等于实测 DRAM 流量。

## 十五、Prefill 大显存预算退化诊断

### 1. 32k 正反复测

延续第十三节的现象，保持同一模型、输入、batch 2048、算子、6 CPU 线程、
host 32768 MiB、reserve 1024 MiB、MTP off，不建立 decode 缓存。
开启原有 `--probe`，按 14336 MiB / 可用显存 / 可用显存 / 14336 MiB 运行。
随后在同样的可用显存预算下，补跑两次 `--prefill-group-layers 1`：

| 项目 | 14336 MiB，自动分组 | 可用显存，自动分组 | 可用显存，单层分组 |
|---|---:|---:|---:|
| Prefill，tok/s | 544.962 / 532.271 | 467.073 / 463.949 | 532.324 / 531.973 |
| 合并吞吐，tok/s | 538.542 | 465.506 | 532.148 |
| 暴露的权重等待，s | 1.615 / 1.639 | 18.311 / 18.467 | 0.382 / 0.374 |
| 分组数 / 最大组层数 | 41 / 4 | 21 / 4 | 45 / 1 |
| 预取层数 | 40 | 20 | 44 |
| 激活 H2D，MiB | 83968 | 43008 | 92160 |
| 激活 D2H，MiB | 81920 | 40960 | 90112 |
| H2D stream 区间，s | 12.664 / 12.668 | 5.631 / 5.630 | 13.594 / 13.598 |
| D2H stream 区间，s | 10.315 / 10.288 | 5.058 / 5.058 | 11.285 / 11.292 |

六次完整 logits 均与原保存结果逐字节相同。权重上传总量仍为 185436.82 MiB；
矩阵产品、native 量化、bounds、attention 调用及 batch 均未变，探针无强制等待。
Layer-pre stream 区间约 24.7–25.8 s，GPU 专家约 18.1–18.7 s，
没有与整体退化同等幅度的计算区间增长。

大预算的激活传输区间确实缩短，但暴露权重等待从平均 1.63 s 增至 18.39 s。
`weight_wait` 包括 bank 构造、分配、必要转换和等待上传，不是单独测量的 DMA 时间。
不能将 H2D/D2H 区间直接相加当墙钟节省，因为它们与计算和权重预取重叠。
在同一大预算下限制单层组，等待降到平均 0.38 s、吞吐恢复，
因此不能把问题归因为“显存更多时 GPU 本身更慢”。

### 2. 对应执行机制

代码路径见 [prefill.cpp](../src/glm5/prefill.cpp) 的 `plan_groups` 和组边界加载，
以及 [weights.cpp](../src/glm5/weights.cpp) 的 `WeightBank`：

1. 自动规划保留默认的下一组一层预取，然后在容量允许时增加当前组层数。
2. 14336 MiB 时，中间大多数 MoE 组为单层，下一组的一层能完整预取。
3. 大预算时，中间大多数 MoE 组变成双层，但仍只预取下一组的一层；
   预取总数从 40 降为 20，不是两层都已准备好。
4. 组边界先等待预取 bank，再为未覆盖的组成员构造无 staging 的 `WeightBank`，
   其上传使用同步 `cudaMemcpy`。增加的 20 个未覆盖层不能被前组计算遮住。
5. 权重总字节没有减少；较少的上传 API 调用也部分来自更多权重改走同步大拷贝，
   不是加载链路变快的证据。

当前 planner 是容量与优先级规划，不是基于实测耗时的成本模型。
“保住预取一层的数量”并不保证“保住下一组的完整覆盖比例”。
这不意味着已有容量检查错误，也不意味着应该对所有上下文固定单层组。

### 3. 当前可用的控制方式

在本次 32k 场景，已有参数可以避免额外同步加载，不需要新速度开关：

```text
--prefill-gpu-mib 0 --prefill-group-layers 1
```

这保留可用显存预算，只限制组大小；代价是更多激活往返。
不是建议所有用户固定单层，也不是把显存预留给 decode。
独立 prefill 完成后才建立 decode 缓存；reserve 仍用于驱动和未计入分配的余量。

### 4. 200k 对照：不能一律限制单层

随后用相同硬件、算子、预算和探针，保持 200000 个输入 ID，做一组

| 暴露的权重等待 | 1.531 s | 17.663 s |
| 分组数 / 预取层数 | 41 / 40 | 21 / 20 |

长输入也暴露了额外的权重加载，但减少激活往返的收益更大，

## 十六、自动分组增加传输机会成本判断

### 1. 新规则

保留原来的“完整层必须放下 → 尽量大 batch → 下一层预取”优先级，
在扩大当前组之前增加一项判断：

```text
若新增层没有被前组预取覆盖，但分到下一组时本可预取：
    只有新增层的实际上传字节 < 本次完整输入的一次激活 H2D 字节，才扩大组。
```

相等时优先预取，不为用满显存而扩大组。若新增层已被前组预取覆盖，
或者原本就无法预取，则不收取这项机会成本。
判断使用实际 native/F32 转换后上传的 tensor payload，不包含 arena 对齐和量化 scratch。
完整输入指本次新增的 suffix，不能用已有 KV 上下文长度让短 append 错选大组。

只计一次 H2D 节省，不将可能被独立 copy engine 隐藏的 D2H 也当作必然墙钟收益。
这是保守的**字节启发式**，不是实测耗时模型，也不是全局最优规划；
尚未估计实际带宽、转换时间、提交成本或预取能否完全完成。
没有写死 32k/200k 阈值，没有增加校准推理、额外权重上传或普通 CLI 速度开关。

自动启用限 CUDA SM86、独立 full-layer、激活流水线且未显式指定组上限。
显式 `--prefill-group-layers N`、关闭流水线、reference 和未验证后端保留原容量规划。
显存、host、transfer、reserve、batch 和预取数量上限均未放宽。

日志新增 `group_policy=transfer|capacity` 和 `unprefetched_weights_mib`。
后者统计没有前组预取覆盖的 trunk tensor payload，包括首组必需加载，
不包含独立 head/NextN bank；它不是实测等待时间或 DRAM 流量。

## 十七、Indexer 寄存器预取流水化

### 1. 两个实现的取舍

Indexer 仍使用 4 查询 × 64 pools 的 tile，32 heads、128 维，
每次按原顺序处理 32 维。每个线程的 8 × 4 个浮点累加器和最终 32 heads 求和不变。

先试额外 shared memory 暂存加 `cp.async`：

- 当前输入必须转置后供计算使用，异步复制先写连续暂存图像，再搬到原转置图像。
- shared memory 从 32768 B 增至 57344 B，寄存器也增加；
  在这版动态 shared 的直接/预取对照中为 80/115 registers，无 stack/local spill。
- 64 查询、50000 pools 的配对微基准，直接约 1.60–1.73 ms，暂存约 2.34–2.40 ms。
- 完整 score 字节、ragged 尾部和保护区检查通过，但明显更慢。
- 已撤掉生产 API 中的异步暂存实现和额外缓冲，仅保留会话内的实验记录。
  该实验的动态 shared 直接路径不是最终保留的基线，不把两轮绝对时间混用。

改用**寄存器预取**后：

- 当前 tile 进入原 shared 图像后，将下一段 query/key 提前读到每线程的
  四个 query `float4`、两个 key `float4`，与当前 tile 的计算交错。
- 下一轮把这些值写进原 shared 图像，再按原 32 维 FMA 顺序计算。
- 没有新增 global/shared 图像，也没有改变权重、输入精度、top-k 或累加顺序。
- 最终原直接 kernel 使用 93 registers，新 kernel 使用 122，
  两者 shared 均为 32768 B、没有 stack/local spill。
- `score_load=prefetch|direct` 显示选择；私有 `DsaScoreLoad` 可独立 A/B。
  没有普通 CLI 速度开关。

自动选择只限已验证的 CUDA SM86、DSA 的 32-head/128-width tiled scorer。
其他架构、reference、scalar/parallel scorer 保留原路径；
该选项不会自行开启 DSA 或 tiled scorer。没有扩展 HIP/SYCL 的自动选择。

### 2. 微基准

同一 RTX 3080，50000 pools，按 direct/prefetch/prefetch/direct、
每个计时样本 20 次运行：

| 查询数 | 原直接路径，ms | 寄存器预取，ms |
|---|---:|---:|
| 1 | 0.119910 / 0.119910 | 0.103117 / 0.103219 |
| 7 | 0.238216 / 0.238438 | 0.206848 / 0.206848 |
| 64 | 1.947954 / 2.248653 | 1.835119 / 1.869158 |

1/7 查询的区间缩短约 14%/13%；64 查询也有收益，但两次原路径绝对时间有波动。
未锁定时钟，也没有硬件计数器测 achieved occupancy、带宽或 stall，
不能只凭寄存器数或预取代码就断定全部收益来自隐藏内存延迟。

### 3. 实模型配对结果

同一 Q4_K_XL 模型、RTX 3080 / W-2133、保存输入，
prefill GPU 14336 MiB、host 32768 MiB、reserve 1024 MiB，
6 CPU 线程、4096 MiB decode 专家缓存上限、DSA/Flash/tail 0、MTP off。
其他已保留优化全部开启，只改变私有 score load 策略。
32k 按 direct/prefetch/prefetch/direct，200k/128 做一组 direct/prefetch：

| 项目 | 原直接路径 | 寄存器预取 |
|---|---:|---:|
| 32768 prefill，tok/s | 551.368 / 544.476 | 549.089 / 548.169 |
| 32768 indexer score stream 区间，ms | 1007.310 / 1055.803 | 914.927 / 911.050 |
| 200000 prefill | 382.421 s，522.984 tok/s | 378.672 s，528.162 tok/s |
| 200000 indexer score stream 区间 | 36.963 s | 32.063 s |

32k 合并吞吐约 +0.13%，整体基本不变；score 区间约缩短 11.49%。
200k 单组整体吞吐约 +0.99%，score 区间约缩短 13.25%（约 4.90 s）。
保留依据是重复微基准和配对模型中的打分阶段收益，不把整体约 1% 说成已排除噪声的普遍提速。
这些 stream 数字是 event 区间，不是硬件测得的 kernel-busy 时间。

六次完整 logits 都与原保存结果逐字节一致，两次长输入全部 128 输出 ID 一致。
同输入规模内，矩阵产品、native 量化、bounds、权重上传、激活 H2D/D2H、
host/global GPU tensor 峰值、score 调用数及 cache hits/misses 全部相同。
32k 仍为 batch 2048、43 组、最多 3 层；200k 为 batch 2048、41 组、最多 4 层。
无新增 host/pinned 内存或 global GPU scratch，探针没有强制等待。
没有宣称 decode 加速；这轮主要验证 prefill 打分热点。
